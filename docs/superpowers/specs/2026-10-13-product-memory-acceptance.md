## 1. Цель и граница решения

Принять один воспроизводимый foundation: authoritative versioned knowledge хранится под существующим Kernel owner, а ограниченный index/граф знаний является восстанавливаемой производной. Свежий агент через обычный вход восстанавливает отношения и пределы, отличает наблюдение от ожидания и гипотезы, сопоставляет изменённые условия, выбирает различающую проверку, сохраняет её результат и передаёт следующему агенту новые знания. Наличие JSON, ссылки, рисунка или сохранённого текста не заменяет эту проверку.

Не создаются второй store, graph DB, runner, обязательный RAG, новый telemetry backend или обход admission. Native graph/catalog/oracle/coverage остаются независимыми. Обоснованная memory relation не становится native `verifies`, approved oracle, execution receipt или основанием уменьшить denominator. Рецепт foundation не закрывает весь V01/L02/K02 и не заменяет связь F07 с E04.

Первый выбранный полный пакет состоит из: (а) deterministic authority/lifecycle/rebuild controls; (б) semantic positive/negative controls; (в) одного producer и трёх matched arms S/R/L, каждый с fresh consumer→nextconsumer, с равным содержанием фактов; (г) controlled scale benchmark. Механизм-only перепроверка двух S-slots допустима для будущего affected repair, но не заменяет этот первый full comparison package. Каждый слой даёт своё решение. Не проводить после каждого PR новый ad hoc live ToolShop pilot. Новые живые проверки для данного пакета не нужны: практическая применимость опирается на уже выполненный scoped ToolShop проход; новое поведение foundation проверяется на сохранённых bytes и явно маркированных controlled targets. Если впоследствии заявляется новое преимущество именно live QA или другой продукт, нужно отдельное подходящее разрешение и evidence, не переименование этих controls.
