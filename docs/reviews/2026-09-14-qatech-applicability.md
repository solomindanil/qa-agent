# QA.tech: вывод коллегии и применимость к qa-agent

Дата: 2026-09-14. Статус: анализ и рекомендации; не разрешение менять
активные кампании, источники, skills или продукт. Независимые агентские роли:
Lead AQA Engineer и AI-архитектор/CTO/product critic. Координатор повторно
прочитал ключевые участки кода и первичную документацию.

## Итог

Направление исследования подходит. Менять архитектуру или создавать ещё один
runner, граф либо сервер памяти не требуется. Заимствуем не рекламное обещание
«автоматизировано всё», а короткий полезный цикл: понять продукт, выбрать
обоснованные проверки, выполнить их, объяснить остаток и перенести проверенный
опыт в следующий запуск.

Сначала заканчиваем уже согласованное продолжение после прерывания. Понятный
handoff входит в этот срез сейчас, а не откладывается вместе с будущей
PR-интеграцией. Затем проверяем переходы внутри одного browser journey;
после — перенос понимания продукта и исправленного правила на свежего агента.

### Важные поправки к первоначальному исследованию

1. **Knowledge revision не обновляет произвольно весь контекст.** Projection,
   discovery и profile зафиксированы; старые requirement targets и blockers
   сохраняются. Это защищает от исчезновения пробелов, но не позволяет обещать
   автоматическое удаление устаревшего правила или обновление discovery.
   Если реальный сценарий упирается в устаревшую запись, нужен отдельный узкий
   проверенный механизм замены с сохранением истории и действующих blockers.
2. **Freeland graph не равен универсальному registration graph.** У specialist
   есть source/impact traversal; текущий универсальный dialect ограничивает
   `requires` связью journey→invariant. Сначала доказываем одну полезную связь,
   а не переносим все виды рёбер по аналогии.
3. **Console dependencies не являются фермой аккаунтов.** Сейчас это сетевые
   разрешения. Новый BrowserContext не изолирует серверный баланс и подписку.
   Последовательное использование проверенного состояния достаточно до тех
   пор, пока конкретная потребность не обосновывает общий allocator.
4. **Краткий handoff не ждёт dashboard.** Он нужен для приёмки текущего recovery:
   ссылки на evidence берутся из reader mapping, сохранённые факты не спрашиваются
   заново, старый PASS не выбирается вместо нового interrupted run.
5. **Один сложный демонстратор не заменяет отдельные gates.** Recovery, качество
   перехода и перенос опыта проверяем раздельно, затем соединяем. Иначе рост
   количества инфраструктурных тестов может скрывать отсутствие полезного QA.

## Ближайшая последовательность без нового движка

1. Завершить текущие Tasks2–7 continuation-плана. Принять через реальные
   Console/Kernel/CLI consumers, cold restore и свежий handoff. Граница —
   anonymous repeat-safe GET известного fixture и живой same-host launcher;
   browser session, host loss, платежи и облако сюда не входят.
2. Согласовать минимальное расширение действующего browser contract для
   промежуточных наблюдений. Переиспользовать evaluator, budgets, guards,
   trace и reader; не вводить язык программирования тестов. При провале
   предусловия зависующее действие не выполняется. Late guard/close failure
   по-прежнему отменяет успешный результат.
3. Один новый продукт/journey: brief → основания требований → компактный
   контекст → выбранные проверки → понятный результат. Известные блокеры,
   недоступные роли и неизвестные области остаются видимыми.
4. Один feedback loop: классифицировать ошибку агента → reviewed bounded
   поправка знаний/проверки → новый близкий пример у свежего агента. Отдельно
   считать первый ответ, подсказки и исправленный прогон. Для слова «слепой»
   answer key должен быть фактически недоступен исполнителю, не просто не
   указан в prompt при общем filesystem.
5. Подключать account provisioning, PR/change entry и дополнительные
   API/MCP/mobile adapters по конкретному оставшемуся пробелу. Затем второй
   host и ограниченный cloud pilot на тех же источниках и контрактах.

Метрики результата: найденные заданные дефекты, ложные баги, ошибочные заявления
«проверено», активные минуты помощи человека, повторные действия после разрыва,
время до полезного заключения. Число тестов/узлов/схем — техническая статистика,
не процент универсальности и не доказательство отсутствия gaps.

## Что пока не переносим

- Отдельный vector/memory server без измеренной проблемы поиска.
- Новый executor, второй verdict engine или активацию reporting-reference.
- Автоматическое превращение отказа пользователя от бага в «никогда не проверять».
- Автоматическую замену бизнес-ожидания ради зелёного теста; адаптация навигации
  и изменение требования имеют разные основания.
- Историческое решение QA.tech показывать зелёный GitHub check для inconclusive
  review. Удобство merge gate не должно подменять честный QA-результат.
- Обещания, что набор receipts, наличие MCP или один успешный eval уже означает
  универсальное тестирование любого продукта либо превосходство над QA.tech.

## Первичные внешние основания

Документация QA.tech отдельно описывает знания для подготовки и выполнения
проверок; исполнитель получает целевой поднабор, а не всю библиотеку.
Это полезная схема отбора контекста, не доказательство качества нашего или их
агента. [Knowledge](https://docs.qa.tech/core-concepts/knowledge).

Их workflow предусматривает цель, условия, просмотр trace, review и повторный
запуск после изменения теста. Это подтверждает ценность управляемого цикла,
а не обещание отсутствия сопровождения.
[Creating Tests](https://docs.qa.tech/best-practices/creating-tests).

Поставщик описывает превращение feedback в правила/память; мы принимаем
механизм как гипотезу пользы и требуем проверки переноса.
[Self-improving PR reviews](https://qa.tech/changelog/2026-09-01).
Ограничение про inconclusive относится к датированному сообщению, а не к
независимой проверке текущего SaaS.
[Check-run controls](https://qa.tech/changelog/2026-06-23).
