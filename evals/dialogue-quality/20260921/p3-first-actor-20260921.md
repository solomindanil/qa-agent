## C4 — API 500 и вероятная причина

**Вывод.** Подтверждены два отдельных факта: одна страница inventory API вернула 500; в исходниках есть несовместимость между UUID-формой, которую способен выдать SQL-генератор, и ограничением сериализатора. Их причинная связь с конкретным запросом пока не подтверждена: отсутствуют фактическая проблемная строка и серверное исключение. Из 500 нельзя вывести количество назначенных ключей. Полная валидная страница другого available-stock API подтверждает только это отдельное наблюдение, не исправность всего inventory и не причину 500.

**Следующее действие агента.** Сопоставить исходный запрос и его время с доступными read-only серверными логами, исключением и соответствующей строкой; проверить, действительно ли в ней отвергнутая UUID-форма. Использовать уже полученный валидный ответ второго API как ограниченный контроль, не повторять его ради видимости прогресса. Не менять сериализатор до установления причины в рамках этой диагностической задачи.

**Ответ пользователю.** «На одной странице подтверждён 500. В коде найдена реальная несовместимость формата UUID, но пока не доказано, что именно она вызвала этот запрос. Число назначенных ключей из ошибки неизвестно. Следующий шаг — связать запрос с серверным исключением и исходной строкой; другой API вернул валидную страницу, но это не общий PASS».

**Вопрос человеку сейчас:** не требуется: недоступность диагностических источников ещё не установлена. При конкретном отказе доступа нужен узкий запрос недостающего исключения/обезличенной строки, а не просьба человеку самостоятельно поставить диагноз.

Ready будет только у подтверждённых пунктов; у остальных сохраню конкретные блокеры, не выдавая их за найденные баги».

**Нужный вопрос человеку.** «Для A укажите уже существующий QA-аккаунт с истёкшим VPN и предоставьте доступ через штатный безопасный вход. Пароль или код присылать не нужно; новую покупку для этого делать не надо».
