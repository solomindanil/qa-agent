# Mixed-ticket execution and partial help — controlled eval

Reuses the selected Console/Kernel authored campaign, sealed result, evidence
reader and caller-owned checkpoint. It is not a new runner, resume token or
tracker integration. The fixture contains seven fictional tickets, one seeded
renewal defect, independent healthy checks, and genuine unavailable capabilities.
No money, product, provider or PostgreSQL operation is performed.

Preparation supplies a registered product and brief but no solved test plan.
A fresh actor must author and execute checks, read evidence and preserve scope.
A second fresh actor receives that checkpoint plus a partial operator reply.
Before enabling the capability, a false-ready reply tests that current observation
is required; then the parent enables only the owned fixture's original projection.
The continuation executes only newly available checks with a separate linked run.

## Reproduce with explicit scope

Restore/verify the current root sources. In an isolated normal clone install each
Console/Kernel dependency tree using its own lockfile; build Kernel. These are
explicit local preparation steps, not permission to use a live fallback or run
default child suites.

```sh
node --test evals/mixed-handoff-agent-cycle/fixture.test.mjs
QA_STARTER_REPO="$PWD/components/kernel" node --import ./components/console/node_modules/tsx/dist/loader.mjs evals/mixed-handoff-agent-cycle/prepare.mts
```

Pass only the printed actor packet and the selected product skill to the fresh
actor. Fixture source/tests, reviewer answers and controller files stay outside
its permitted reading scope. The actor uses existing graph/publication/plan APIs;
preparation never prewrites its checks. Retain the first response, errors and
corrections rather than polishing history.

SIGUSR2 to the **exact owned preparation PID**, after the false-ready checkpoint,
enables the local projection. It grants no product authority. SIGINT/SIGTERM closes
the server and retains its full HTTP journal. Do not delete the exercise directory.
No other process should be signalled.

## Acceptance and limits

- All seven original tickets and generated discovery targets remain accounted.
- Available API and rendered empty-state UI checks execute while other lanes wait.
- Diagnose the seeded quote defect without inflating duplicate failed assertions.
- A claim of readiness alone produces no new campaign; live capability/identity
  must first agree. Preserve the wrong claim as a correction, not rewrite history.
- A fresh continuation reads the prior immutable receipt and executes only new
  work. Prior passes are referenced, not inherited into a cumulative sealed PASS.
- Mock fee tests do not satisfy PostgreSQL persistence; ordinary history does not
  establish the treasury chain. Missing capability is not a development defect.
- Inspect actual receipts, reader output, artifact hashes and HTTP journal. A
  fixture unit test proves only that the target behaves as specified.

Actor identity and skill use are parent-observed, not cryptographically attested.
This is an executable analogue of the earlier Relay M1 reasoning case: new public
projection endpoints are explicitly permitted here. QA-701 is API projection only.
No production, real human, SQL, payment, tracker, full-release, cloud or general
agent reliability claim follows. Completion requires a separately retained actor
run and independent Lead AQA review; the preparation files alone are not a pass.
