# Nuanu App Flow Control Plane Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a durable fail-closed confirmed-defect outbox and create the
private Nuanu Flow workspace, project, Bugs workflow, labels, views, and
campaign-level coverage backlog with exact read-back.

**Architecture:** A private append-only journal is the local authority until a
Flow item is created and read back. Lease acquisition, renewal, commit, and
release use the same immutable contiguous event sequence, so a newer
`leaseId`/fence publication prevents a paused older writer from overwriting
state. `flow-outbox.snapshot.v1.json` and `flow-outbox.json` are rebuildable
caches after journal genesis. A descriptor-bound host adapter searches by an
immutable fingerprint before a create and requires an action-time host
confirmation bound to the immutable exact batch. A successful request is never
treated as remote success without read-back. An ambiguous create fails closed
and must be reconciled before another create; without a server-side
idempotency key this plan deliberately does not claim global exactly-once
delivery. The currently unproven attachment read-back capability is an
explicit post-create blocker, not an inferred success. Nuanu Flow is a control
plane, not a test execution dependency.

**Tech Stack:** Node.js ESM, node:test, atomic filesystem persistence, Nuanu
Flow compact MCP tools.

**Spec:** `docs/superpowers/specs/2026-08-26-nuanu-app-qa-project-design.md`

## Locked Append-Only Journal Contract

This section governs Task 2 and every later task. Task 1 is a frozen historical
record of the already-committed mutable-JSON baseline at `74f997a` plus its
UTF-8 prerequisite at `7145c88`; its lock/storage steps are not re-executed or
reinterpreted as journal work. Task 2 alone replaces that authority/publication
layer and extends the opaque transaction with journal fencing. Task 1's
canonical JSON model, privacy validation, transition validator, and exact
five-method service shape are inputs. Tasks 3–7 consume the same canonical
outbox and transaction methods without receiving journal paths or append
capability.

### Fixed paths, names, modes, and caps

Production uses only these module-derived paths:

~~~text
PRIVATE_ROOT/flow-outbox.journal.v1/
PRIVATE_ROOT/flow-outbox.snapshot.v1.json
PRIVATE_ROOT/flow-outbox.json
PRIVATE_ROOT/flow-outbox.lock
PRIVATE_ROOT/flow-outbox.lock.reclaim
PRIVATE_ROOT/.flow-outbox-journal-candidate-v1-<publicationId>.json
PRIVATE_ROOT/.flow-outbox-migration-barrier-v1-<publicationId>.json
~~~

The first three are respectively authority, optional replay-checkpoint cache,
and compatible projection cache. The lock path becomes a permanent,
non-authoritative compatibility barrier before genesis; the reclaim path must
always be absent. Candidate names are internal, use a freshly generated
lowercase UUIDv4 `publicationId`, and are never accepted from a public method,
CLI argument, environment variable, finding, action, or observation.

The journal directory is mode `0700`. Published sequence files are mode `0400`
and match exactly `/^[0-9]{20}\.json$/`; sequence one is
`00000000000000000001.json`. Candidates are created mode `0600`, fsynced, then
changed to `0400` before publication. Snapshot and projection are mode `0600`
through the existing hardened atomic JSON writer. Readers reject symlinked or
non-directory journal paths and symlinked/non-regular sequence files. Candidate
residue lives outside the journal directory and is never part of replay.

Add and export these exact code-owned caps:

~~~js
export const MAX_JOURNAL_EVENTS = 100_000;
export const MAX_JOURNAL_TOTAL_BYTES = 2 * 1024 * 1024 * 1024;
export const MAX_JOURNAL_EVENT_BYTES = MAX_OUTBOX_BYTES + 64 * 1024;
export const MAX_OUTBOX_SNAPSHOT_BYTES = MAX_OUTBOX_BYTES + 64 * 1024;
export const MAX_JOURNAL_CANDIDATES = 16;
export const MAX_JOURNAL_CANDIDATE_TOTAL_BYTES =
  MAX_JOURNAL_CANDIDATES * MAX_JOURNAL_EVENT_BYTES;

~~~

The existing `MAX_OUTBOX_BYTES = 4 * 1024 * 1024`, `MAX_ENTRIES = 500`,
finding/attachment limits, `MAX_LEASE_MS`, action limits, descriptor limit, and
observation limit do not change. Replay sums attested sequence-file sizes
before allocating or parsing them and enforces both event-count and total-byte
caps. Each bounded read uses fatal UTF-8 and stable-metadata double-read
attestation. A new event that would exceed any cap fails before candidate
creation with `OUTBOX_JOURNAL_LIMIT_EXCEEDED`.

The injected `journalFs` surface is exact: `open`, `lstat`, `readdir`, `mkdir`,
`link`, and `unlink`. Handles returned by `open` supply only the required
`stat`, bounded `read`/complete `write`, `fsync`, `chmod`, and `close`
operations. Journal publication never receives or uses rename, destination
unlink, recursive removal, or caller-selected paths. Production binds this
surface to Node filesystem primitives; temporary tests may wrap it to record or
pause the exact operations.

The new storage error set is closed:

| Code | Exact condition |
| --- | --- |
| `INVALID_OUTBOX_JOURNAL` | journal path/entry/schema/UTF-8/digest/sequence/mode/replay invariant fails |
| `INVALID_OUTBOX_JOURNAL_CANDIDATE` | candidate prefix/name/type/mode/stable metadata is invalid, or cleanup cannot re-attest either this exact candidate or no-follow absence |
| `OUTBOX_JOURNAL_LIMIT_EXCEEDED` | next event or replay exceeds event, event-count, or total-byte cap |
| `OUTBOX_JOURNAL_ORPHAN_LIMIT_EXCEEDED` | candidate inventory exceeds 16 files, per-file cap, or aggregate candidate cap |
| `OUTBOX_JOURNAL_PUBLISHER_UNQUIESCED` | a bounded candidate is not the attested second link of an already-published event |
| `OUTBOX_JOURNAL_ORPHAN_CLEANUP_FAILED` | post-unlink lstat proves this call's exact candidate remains; it blocks publication |
| `OUTBOX_JOURNAL_CANDIDATE_CLEANUP_DURABILITY_UNKNOWN` | post-unlink lstat proves candidate absence, but the following private-root fsync fails; no candidate is currently present |
| `OUTBOX_JOURNAL_INVENTORY_DURABILITY_UNKNOWN` | mandatory private-root fsync at the end of bounded candidate inventory, or after the no-unlink event `candidateState:ABSENT × destination:MATCHING` branch, fails when this call performed no candidate unlink; excludes journal-directory create/adopt durability and first barrier visibility durability |
| `OUTBOX_JOURNAL_DIRECTORY_DURABILITY_UNKNOWN` | the journal directory was created/adopted but the pre-publication private-root fsync failed; no event is linked |
| `OUTBOX_JOURNAL_PUBLICATION_UNSUPPORTED` | oracle cell is `THROWN(UNSUPPORTED) × ABSENT`, where unsupported is EXDEV, EPERM, EOPNOTSUPP, or ENOTSUP |
| `OUTBOX_JOURNAL_PUBLICATION_FAILED` | oracle cell is `THROWN(OTHER) × ABSENT` |
| `OUTBOX_JOURNAL_PUBLICATION_INCONSISTENT` | oracle cell is `RETURNED × DIFFERENT_VALID`, `RETURNED × ABSENT`, or `THROWN(EEXIST) × ABSENT` |
| `OUTBOX_JOURNAL_CAS_LOST` | oracle cell is `THROWN(EEXIST|UNSUPPORTED|OTHER) × DIFFERENT_VALID`; acquisition must replay rather than retarget inside publication |
| `OUTBOX_JOURNAL_DURABILITY_UNKNOWN` | oracle destination is `MATCHING` or `DIFFERENT_VALID`, but its post-link journal-directory fsync did not complete |
| `OUTBOX_LEASE_FENCED` | a transaction event loses its expected tail or current lease/fence to a different published event |
| `OUTBOX_LEGACY_BUSY` | a non-barrier legacy lock or any reclaim path exists before genesis |
| `OUTBOX_LEGACY_BARRIER_DURABILITY_UNKNOWN` | an exact barrier is visible during create/adopt but the required private-root fsync did not complete |
| `OUTBOX_LEGACY_BARRIER_INVALID` | after genesis, the required barrier path is malformed, symlinked, non-regular, or wrong-mode |
| `OUTBOX_LEGACY_BARRIER_LOST` | after genesis, the bound barrier is missing or its canonical record/digest no longer equals genesis |

Existing `OUTBOX_LOCKED`, `OUTBOX_LEASE_EXPIRED`, transaction, transition,
privacy, finding, action, and receipt codes retain their meanings. Provider or
raw filesystem messages are never copied into these errors or persisted.

### Permanent legacy-writer compatibility barrier

Automatic migration is permitted only after the new implementation has
excluded every cooperating Task 1/old Task 2 writer with the path they already
honor. Before it reads the legacy projection for genesis, Task 2 publishes this
exact old-lock-compatible record at fixed `flow-outbox.lock`:

~~~js
{
  ownerId: "journal-v1-barrier-<lowercase UUIDv4>",
  acquiredAt: "canonical injected UTC instant",
  expiresAt: "9999-12-31T23:59:59.999Z",
}
~~~

The canonical record digest is `sha256:` plus `digestJson(record)`. The owner
matches exactly
`/^journal-v1-barrier-[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/`.
The far-future canonical expiry is deliberate: committed Task 1 treats any
existing lock as held, and the uncommitted stale-reclaim implementation treats
this exact record as unexpired. The barrier is not the new authority and is
never renewed; it exists permanently to prevent an old binary from resuming
projection writes or dispatching stale actions after journal genesis.

Create a complete mode-0600 barrier candidate under the fixed private root
with O_EXCL/no-follow, write/fsync/close it, hard-link it once to
`flow-outbox.lock` once. Never create a partial lock record directly. Before
candidate creation, any reclaim path or any lock other than an exact canonical
journal barrier is `OUTBOX_LEGACY_BUSY`; do not reclaim, wait, mutate, delete,
or infer expiry. An exact pre-existing barrier is adopted after attestation and
private-root fsync without creating or linking a candidate.

When this call does link a barrier candidate, use the same normalized
`RETURNED|THROWN(errorClass)` outcome and mutually exclusive destination oracle
as the event matrix, substituting mode `0600`, the fixed lock path, and
private-root fsync. `MATCHING` is this candidate's exact barrier bytes/inode.
`DIFFERENT_VALID` is only another exact canonical journal barrier with a
different owner/digest. `ABSENT` is no-follow `ENOENT`; `INVALID` is every
other lock-path state and maps to `OUTBOX_LEGACY_BUSY` without cleanup. The
literal cell results are otherwise the same: `PUBLISHED` installs this barrier;
`THROWN(*) × DIFFERENT_VALID` fsyncs, cleans this call's candidate, and adopts
the attested barrier; `RETURNED × DIFFERENT_VALID` is
`OUTBOX_JOURNAL_PUBLICATION_INCONSISTENT`; the three `ABSENT` results use the
same unsupported/failed/inconsistent codes. There is no automatic link retry;
only `THROWN(OTHER) × ABSENT` permits a later fresh mutating call.

Barrier cleanup is limited to the same three tokens: `PUBLISHED`, `CAS_LOST`,
and `FAILED`; inconsistent, unsupported, and invalid barrier cells retain their
candidate and block later mutation. For
`candidateState:ABSENT × destination:MATCHING`, re-attest no-follow absence,
skip unlink, and fsync the private root once. Success adopts the published
barrier. Failure is `OUTBOX_LEGACY_BARRIER_DURABILITY_UNKNOWN`, preserves the
barrier, and requires a fresh mutator to re-attest/fsync it without relinking;
it is not candidate-cleanup uncertainty.

Barrier candidate cleanup uses the same two phases. If the candidate remains,
`OUTBOX_JOURNAL_ORPHAN_CLEANUP_FAILED` blocks; if absence is proven but the
following private-root fsync fails,
`OUTBOX_JOURNAL_CANDIDATE_CLEANUP_DURABILITY_UNKNOWN` recovers by the mandatory
empty-inventory root fsync on a fresh call. If an exact barrier is visible but
its first private-root durability fsync fails, preserve it, publish no genesis,
and return `OUTBOX_LEGACY_BARRIER_DURABILITY_UNKNOWN`; the next mutating call
re-attests and fsyncs it without relinking.

After the barrier wins or is adopted, re-attest its inode and canonical digest,
recheck that `.reclaim` is absent, and only then read the legacy projection.
Re-attest the same barrier immediately before the genesis hard link. Bind
`legacyBarrierDigest` into `bootstrap_v1`. Every journal replay, including
`readOutbox`, requires the current barrier to match genesis. Missing or changed
barrier after genesis is `OUTBOX_LEGACY_BARRIER_LOST`; malformed/symlinked/
non-regular/wrong-mode barrier is `OUTBOX_LEGACY_BARRIER_INVALID`. No projection
or journal operation continues without it. The service never deletes the
barrier. This closes the old-reader/old-writer TOCTOU instead of treating an
absence check as quiescence.

### Canonical event and digest schema

Every published event is exact closed JSON:

~~~js
{
  schemaVersion: 1,
  sequence: 1,                         // safe integer; equals filename
  publicationId: "00000000-0000-4000-8000-000000000000", // UUIDv4 shape
  kind:
    | "bootstrap_v1"
    | "lease_acquired"
    | "lease_renewed"
    | "outbox_committed"
    | "lease_released",
  recordedAt: "canonical UTC instant",
  previousEventDigest: null | "sha256:<64 lowercase hex>",
  previousOutboxDigest: null | "sha256:<64 lowercase hex>",
  nextOutboxDigest: "sha256:<64 lowercase hex>",
  leaseId: null | "lowercase UUIDv4",
  fenceSequence: 0,                    // zero or positive safe integer
  payload: {},                         // exact kind union below
  eventDigest: "sha256:<canonical preceding fields>",
}
~~~

`previousEventDigest` and `previousOutboxDigest` are null together only for
sequence one. For every later event, `previousEventDigest` equals the preceding
event's recomputed digest and `previousOutboxDigest` equals the replayed outbox
digest before the event. `nextOutboxDigest` equals the digest after the event.
`eventDigest` is `sha256:` plus `digestJson` of every preceding top-level field
in the shown order; `digestJson` recursively sorts object keys and preserves
array order. The outbox digest is `sha256:` plus `digestJson` of the exact
canonical `{version:1,entries}` object. Existing finding, action, batch, and
receipt digest algorithms do not change.

Both generated identity classes match exactly
`/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/`.
Every `publicationId` is journal-unique. Every acquired `leaseId` is distinct
from all prior acquisitions; renewal, commit, and release must repeat their
current acquisition's lease ID.

Journal validation reuses the exact closed-JSON, owner-ID, outbox, finding,
action, observation, secret-key, and privacy-unsafe-value validators. Events
contain only the canonical outbox, code-owned enums/digests, internal UUIDs,
bounded owner ID, and canonical timestamps. They never persist a candidate
pathname, process ID, provider error/message/stack, credential, raw response,
descriptor body, attachment bytes, or private evidence path. Filesystem errors
map only to the code-owned error codes in this contract.

The payload union and state effects are exact:

| Kind | Top-level lease/fence | Exact payload | Replay effect |
| --- | --- | --- | --- |
| `bootstrap_v1` | `leaseId:null`, `fenceSequence:0` | `{source:"empty_v1"|"legacy_v1_projection",legacyBarrierDigest,outbox}` | sequence one only; validates permanent barrier and installs complete V1 outbox; active lease remains null |
| `lease_acquired` | fresh `leaseId`, `fenceSequence === sequence` | `{ownerId,acquiredAt,expiresAt}` | outbox digest unchanged; install active lease |
| `lease_renewed` | current `leaseId`, `fenceSequence === sequence` | `{ownerId,acquiredAt,previousExpiresAt,expiresAt,previousFenceSequence}` | outbox digest unchanged; retain lease identity and advance fence |
| `outbox_committed` | current `leaseId` and current fence | `{outbox}` | validate exact old-to-new outbox transition, install complete outbox, clear active lease atomically |
| `lease_released` | current `leaseId` and current fence | `{}` | outbox digest unchanged; clear active lease |

`bootstrap_v1.recordedAt`, lease acquisition/renewal times, commit time, and
release time use the injected clock and are canonical UTC instants. Journal
times are nondecreasing. Acquisition requires no active lease or
`activeLease.expiresAt < recordedAt`; equality is still locked. Its
`recordedAt === acquiredAt` and `expiresAt === acquiredAt + leaseMs`.
Renewal requires `recordedAt < current expiresAt`, preserves `ownerId`,
`leaseId`, and `acquiredAt`, requires the exact prior expiry/fence in payload,
and sets `expiresAt === recordedAt + leaseMs`. Commit requires
`recordedAt < current expiresAt`. Release may clear an exact still-current
lease even after expiry, but cannot clear or alter a newer lease. Lease events
have identical previous/next outbox digests. Only bootstrap and commit embed an
outbox. Unknown fields, enum values, events, payload variants, digest forms,
and transitions fail `INVALID_OUTBOX_JOURNAL`.

Replay returns exactly:

~~~js
{
  throughSequence,
  throughEventDigest,
  outbox,
  outboxDigest,
  activeLease: null | {
    leaseId,
    ownerId,
    acquiredAt,
    expiresAt,
    fenceSequence,
  },
  totalBytes,
}
~~~

Directory entries must be the exact contiguous sequence `1..throughSequence`.
An empty/missing journal has no replay result and enters the bootstrap rules
below. Any gap, unexpected journal entry, filename/sequence mismatch, invalid
mode, oversized file/set, digest-chain mismatch, outbox-digest mismatch,
duplicate acquired-lease/publication identity, time regression, or illegal state effect
rejects the entire authority. Replay never skips a bad event, selects a later
branch, or repairs published history.

### Journal-directory genesis

`readOutbox` never creates a missing journal directory. The first mutating call
first wins/adopts and attests the permanent compatibility barrier, then calls
one private `ensureJournalDirectory()`:

1. Attest the fixed private root and open it no-follow as a directory.
2. `mkdir(flow-outbox.journal.v1, {mode:0o700})` once, without `recursive`.
3. On success or `EEXIST`, lstat the exact path, reject a symlink/non-directory/
   wrong mode, open it `O_RDONLY|O_DIRECTORY|O_NOFOLLOW`, fstat it, and require
   the opened inode to equal the lstat inode.
4. Re-attest the private-root inode and fsync the private-root directory before
   any candidate or sequence publication. A newly created directory is not
   usable before that fsync succeeds.

Concurrent creators are deterministic: one `mkdir` succeeds, the others receive
`EEXIST` and adopt only the same attested `0700` directory. A crash before
`mkdir` leaves it absent; a crash after `mkdir` leaves it absent or an empty
directory. The next mutating call repeats the full attestation and parent
fsync, then publishes sequence one. A nonempty directory must pass ordinary
contiguous replay; it is never reset as an incomplete creation. Parent fsync
failure returns `OUTBOX_JOURNAL_DIRECTORY_DURABILITY_UNKNOWN`, publishes no
event and creates no event candidate, and is reconciled by a later mutating
call repeating this exact attestation/fsync. That later call may publish only
after the root fsync succeeds. It is safe to retry from a fresh public call
because replay still has no new event; the failed call never retries itself.
This pre-link result is distinct from
`OUTBOX_JOURNAL_DURABILITY_UNKNOWN`, which requires a visible linked event and
forbids operation retry before replay. Creation never removes, renames,
chmod-repairs, or recursively replaces an existing path.

### Bounded candidate inventory and recovery

Every `readOutbox`/replay and every publication first lists the fixed private
root and inventories every name beginning
`.flow-outbox-journal-candidate-v1-` or
`.flow-outbox-migration-barrier-v1-`. A prefix match with a non-exact UUIDv4
suffix/`.json` form, symlink, non-regular entry, a journal-candidate mode other
than `0600` or `0400`, a barrier-candidate mode other than `0600`, size above
`MAX_JOURNAL_EVENT_BYTES`, more than 16 candidate files, or aggregate
candidate bytes above `MAX_JOURNAL_CANDIDATE_TOTAL_BYTES` fails closed before
a new candidate is created. Invalid name/type/mode is
`INVALID_OUTBOX_JOURNAL_CANDIDATE`; an over-cap inventory is
`OUTBOX_JOURNAL_ORPHAN_LIMIT_EXCEEDED`; metadata that changes during the
bounded double-read is `OUTBOX_JOURNAL_PUBLISHER_UNQUIESCED`. The scan sorts
names and uses lstat/open/fstat stable-metadata bounded reads. A mode-0600
journal candidate is an in-progress publisher and is never parsed, repaired,
or removed by another service; mutation treats it as unquiesced. Read/replay
performs no candidate deletion and may ignore a valid within-cap candidate
after inventory. Candidates are outside the journal and never affect outbox
replay, but they cannot accumulate outside a cap.

A test-only pause before the underlying journal-candidate `O_EXCL` open leaves
no candidate and therefore does not block a later fresh mutator. Once that
`O_EXCL` succeeds, every fresh mutator applies the ordinary inventory rules:
it may not bypass, ignore, or age-delete the candidate. The expired-writer
fencing witness below pauses before candidate creation; the separate
crash-before-link witness continues to prove that an already-created unmatched
candidate blocks all fresh mutation until publisher quiescence is proven.

A mode-0400 journal candidate whose parsed exact event, `publicationId`,
digest, inode, and bytes match its published sequence path is post-link residue.
A mode-0600 barrier candidate whose exact record and inode match the permanent
barrier is likewise published residue. Before a mutation, remove each such
attested candidate through the two-phase cleanup primitive. A pre-absence
failure leaves the candidate present and returns
`OUTBOX_JOURNAL_ORPHAN_CLEANUP_FAILED`; a post-absence private-root fsync
failure returns `OUTBOX_JOURNAL_CANDIDATE_CLEANUP_DURABILITY_UNKNOWN` with no
candidate currently present. Neither revokes the destination. Every mutating
inventory ends with a private-root fsync even when no candidates are present;
no new candidate may be created until it succeeds. This mandatory empty-
inventory fsync is the fresh-call recovery for a prior post-absence durability
error. If it fails on a call that performed no candidate unlink, return
`OUTBOX_JOURNAL_INVENTORY_DURABILITY_UNKNOWN`; create/link nothing and let only
a later fresh mutation repeat inventory plus root fsync. This code never
replaces `OUTBOX_JOURNAL_DIRECTORY_DURABILITY_UNKNOWN` for journal-directory
create/adopt or `OUTBOX_LEGACY_BARRIER_DURABILITY_UNKNOWN` for first barrier
visibility durability.

Every other bounded candidate may be an active publisher or a pre-link crash.
`readOutbox` may ignore it as non-authoritative after the bounded inventory,
but a mutating call fails `OUTBOX_JOURNAL_PUBLISHER_UNQUIESCED` and creates no
candidate. It is never age-guessed or automatically deleted. An operator may
remove it only after separately proving no publisher is live. This fail-closed
rule and the candidate caps replace the prior unbounded "ignore residue"
behavior. The publisher also reserves one candidate slot and its serialized
bytes before O_EXCL creation, so its own new candidate cannot cross either cap.

### Publication linearization and fencing

Implement one private `publishEvent({expectedTail, buildEvent})` primitive.
It performs these exact steps:

1. Complete the bounded candidate inventory/cleanup, then re-attest the fixed
   private root and already parent-fsynced `0700` journal directory. Derive only
   `expectedTail.throughSequence + 1` and its 20-digit destination; callers
   cannot supply a sequence or destination.
2. Generate a fresh UUIDv4 publication ID, build and canonicalize one event,
   recompute all state/event digests, serialize with a trailing newline, and
   enforce event/count/total-byte caps.
3. Create the same-private-root candidate with
   `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW`, mode `0600`; attest the inode, write
   every byte, fsync, chmod `0400`, fsync again, close, and re-attest identical
   inode/content metadata.
4. Immediately re-read the current authoritative tail. A changed tail aborts
   this candidate before publication. For a transaction event, also require
   current active `leaseId`, `fenceSequence`, expiry, and snapshot digest.
   When any of those bindings changed after candidate completion, do not call
   `link`. Re-attest and remove only this call's exact candidate through the
   ordinary two-phase cleanup primitive, including its required private-root
   fsync, and return
   `OUTBOX_LEASE_FENCED` for a transaction event. A pre-absence cleanup failure
   or post-absence durability failure overrides that disposition with its
   existing closed cleanup code. This is publisher-local stale-candidate
   cleanup, not orphan recovery, and never permits age-based deletion.
5. Invoke `link(candidatePath, exactSequencePath)` once. No rename, overwrite,
   unlink-destination, mutable lock, or process-local serialization is a
   substitute. Normalize the syscall to exactly
   `{kind:"RETURNED"}` or
   `{kind:"THROWN",errorClass:"EEXIST"|"UNSUPPORTED"|"OTHER"}`.
   `UNSUPPORTED` is exactly `EXDEV|EPERM|EOPNOTSUPP|ENOTSUP`; raw error text is
   discarded.
6. After every return or throw, re-attest the journal-directory inode, this
   call's candidate identity, and the exact destination. Candidate state is
   first classified `EXACT`, `ABSENT`, or `INVALID`. `ABSENT` may proceed only
   when the destination is `MATCHING`, because another reconciler may already
   have cleaned published residue; `INVALID` is
   `INVALID_OUTBOX_JOURNAL_CANDIDATE` and is never unlinked. Only an `EXACT`
   candidate enters every other matrix cell.
7. Classify the destination into exactly one mutually exclusive state.
   `MATCHING` is this event's exact canonical bytes, `publicationId`,
   `eventDigest`, mode `0400`, and the same inode while the candidate is
   `EXACT`. `DIFFERENT_VALID` is a mode-0400 canonical event at the expected
   sequence that validates from `expectedTail` and has a different
   publication identity/digest. `ABSENT` is no-follow `ENOENT`. `INVALID` is
   every remaining state, including symlink, wrong type/mode, unstable
   metadata, noncanonical bytes, invalid transition, or same bytes on a
   different extant inode. No prose alias or errno may reclassify a cell.
8. Apply the literal 16-cell oracle below. `PUBLISHED` fsyncs the journal
   directory and, for an `EXACT` candidate, runs cleanup before accepting this
   event once. `CAS_LOST` fsyncs the journal directory, runs cleanup, and
   replays the `DIFFERENT_VALID` event; bootstrap adopts only an identical
   payload, acquisition returns `OUTBOX_JOURNAL_CAS_LOST` for outer replay,
   and renewal/commit/release return `OUTBOX_LEASE_FENCED`. `FAILED` runs
   cleanup against the attested-absent destination before returning
   `OUTBOX_JOURNAL_PUBLICATION_FAILED`. These are the only three cell tokens
   allowed to unlink a candidate. `INCONSISTENT` fsyncs a `DIFFERENT_VALID`
   destination when present but deliberately retains the candidate, then
   returns `OUTBOX_JOURNAL_PUBLICATION_INCONSISTENT`. `UNSUPPORTED` retains the
   candidate and returns its named code. `INVALID` leaves both paths untouched
   and returns `INVALID_OUTBOX_JOURNAL`.

| Normalized link outcome | `MATCHING` | `DIFFERENT_VALID` | `ABSENT` | `INVALID` |
| --- | --- | --- | --- | --- |
| `RETURNED` | `PUBLISHED` | `INCONSISTENT` | `INCONSISTENT` | `INVALID` |
| `THROWN(EEXIST)` | `PUBLISHED` | `CAS_LOST` | `INCONSISTENT` | `INVALID` |
| `THROWN(UNSUPPORTED)` | `PUBLISHED` | `CAS_LOST` | `UNSUPPORTED` | `INVALID` |
| `THROWN(OTHER)` | `PUBLISHED` | `CAS_LOST` | `FAILED` | `INVALID` |

There is no in-primitive link retry or retarget. `PUBLISHED` is never
republished. `CAS_LOST` permits only outer replay and a later fresh acquisition
call. `FAILED` alone permits a later fresh public-call publication retry after
replay. `UNSUPPORTED`, `INCONSISTENT`, and `INVALID` are nonretryable: their
candidate is never unlinked by the cell, so the next mutation is physically
blocked as unquiesced until filesystem/operator review. They cannot collapse
through cleanup-fsync uncertainty into a retryable empty inventory.

`candidateState:ABSENT × destination:MATCHING` is the executable `PUBLISHED`
subcase after another reconciler removed published residue. Fsync the journal
directory, lstat the candidate path again and require no-follow `ENOENT`, skip
unlink entirely, then fsync the private root. Root-fsync success returns
`PUBLISHED`; failure is
`OUTBOX_JOURNAL_INVENTORY_DURABILITY_UNKNOWN`, retains the matching event, and
requires a fresh mutating inventory/root-fsync before replayed success. It is
never classified as orphan cleanup or post-unlink cleanup uncertainty.

Cleanup has two mutually exclusive failure phases. Before unlink, require this
call's recorded candidate inode/type/mode/bytes and invoke unlink once. Then
lstat the candidate path: if the same candidate remains,
`OUTBOX_JOURNAL_ORPHAN_CLEANUP_FAILED` overrides the cell result and that
candidate blocks publication; if another entry appears or re-attestation
cannot prove exact-candidate-or-absence,
`INVALID_OUTBOX_JOURNAL_CANDIDATE` overrides and nothing further is unlinked. Once
lstat proves `ENOENT`, candidate absence is established regardless of unlink's
return/throw. Fsync the private root. Failure of only this post-absence fsync is
`OUTBOX_JOURNAL_CANDIDATE_CLEANUP_DURABILITY_UNKNOWN`, not orphan cleanup; no
candidate is currently present. Every later mutating call completes candidate
inventory and fsyncs the private root even when inventory is empty before it
may create a candidate. That fresh-call fsync is the exact recovery; if the
candidate reappears after a crash, ordinary bounded recovery classifies it.
This post-unlink error can arise only from cleanup-eligible `PUBLISHED`,
`CAS_LOST`, or `FAILED`. After the fresh-call root fsync, destination replay
preserves the original disposition: `MATCHING` is already published and is
never retried, `DIFFERENT_VALID` replays CAS loss without retargeting, and
`ABSENT` permits only the later fresh retry already allowed by `FAILED`.

If the oracle destination is `MATCHING` or `DIFFERENT_VALID` but the
journal-directory fsync fails, do not unlink or roll back the event. Throw
`OUTBOX_JOURNAL_DURABILITY_UNKNOWN`; the next command must replay and reconcile
whether the event is present before any retry. In a
`THROWN(*) × DIFFERENT_VALID` cell, cleanup only this call's attested candidate
before returning durability unknown; apply the two cleanup phases above. In
`RETURNED × DIFFERENT_VALID` and every `* × MATCHING` cell, retain the
candidate so the pending nonretryable/published disposition cannot collapse.
A later recovery after process or power loss sees either the complete event or
the preceding contiguous tail, never a partial event.

The successful hard-link creation is the linearization point. A crash before
it leaves no authoritative event. A crash after it leaves one complete event;
recovery replays that event even when the candidate hard link also remains.
An operation that lost stdout or received a post-link error must replay before
retrying. The existing fingerprint/receipt/action state then makes safe reads
and duplicate enqueues idempotent, while a dispatched create retains its
existing ambiguity rules. Published events are never rolled back to make an
API call appear unsuccessful.

Lease acquisition itself is a journal publication. Contenders for an expired
lease construct different lease IDs for the same next sequence; exactly one
hard link wins. The winner's event sequence is its fence. `renew` appends an
event and updates the transaction's read-only `fenceSequence` getter. `commit`
can publish only against that latest fence and clears the lease in the same
event. Thus the critical race is serialized as:

~~~text
old lease fence N -> old commit pauses before candidate O_EXCL
new owner publishes lease N+1 and commit N+2
old writer completes its stale N+1 candidate -> mandatory pre-link replay sees N+2
old exact candidate cleanup -> zero link calls -> OUTBOX_LEASE_FENCED
~~~

No mutable lock inode, hard-linked reclaim marker, owner rewrite, or stale-file
deletion participates in journal serialization. The permanent legacy barrier
participates only in old-worker exclusion and is digest-bound at genesis.

### Bootstrap, caches, and V1 retention

When no sequence-one event exists, `readOutbox` reads the fixed legacy
projection with existing hardened bounded JSON I/O. A missing file yields the
empty V1 outbox; a valid file returns its canonical state without writing.
Malformed, invalid-UTF-8, oversized, symlinked, non-regular, privacy-unsafe, or
transition-invalid legacy state fails closed.

The first mutating call wins or adopts the permanent legacy-writer barrier,
ensures and parent-fsyncs the journal directory, clears only attested published
candidate residue, then reads the legacy projection while the barrier excludes
old writers. It re-attests the barrier and absent reclaim path immediately
before publishing sequence one as `bootstrap_v1`, with the barrier digest,
`source:"legacy_v1_projection"`, and the exact canonical legacy outbox or
`source:"empty_v1"` and `{version:1,entries:[]}`. Concurrent bootstrappers first
adopt the same barrier, then use different publication IDs for the same
sequence slot; the loser discards its candidate, validates the winning genesis
and barrier digest, and continues only from that journal. After sequence one
exists, projection bytes are never an authority or migration input again, and
every operation re-attests the permanent barrier before trusting replay.

The optional snapshot schema is exact:

~~~js
{
  schemaVersion: 1,
  throughSequence,
  throughEventDigest,
  outbox,
  outboxDigest,
  activeLease: null | { leaseId, ownerId, acquiredAt, expiresAt, fenceSequence },
  snapshotDigest: "sha256:<canonical preceding fields>",
}
~~~

A snapshot may avoid applying already-covered outbox states only after replay
has validated the immutable filename/event/digest chain through its
`throughSequence`. Its wrapper digest, bound event digest, outbox digest, and
active lease must all match that prefix. Missing, stale, future, malformed,
oversized, symlinked, or mismatched snapshots are ignored and full replay is
used; they never invalidate a valid journal. The projection remains the exact
V1 `{version,entries}` object, with no wrapper fields, so Tasks 3–7 and existing
operators see the same state shape.

After a successfully directory-fsynced event, atomically refresh snapshot;
refresh projection only when bootstrap or commit changes the outbox. These are
best-effort cache writes after the authoritative linearization point. Failure,
process death, or stale bytes in either cache does not make the journal commit
fail and cannot authorize a retry. `readOutbox`, transaction snapshots, action
IDs, recovery, and every transition always use replay output. A later event may
refresh both caches. V1 performs no automatic compaction: it never deletes a
sequence file or promotes a snapshot to genesis. At a cap it fails closed with
`OUTBOX_JOURNAL_LIMIT_EXCEEDED`; a separately reviewed later schema/version
must define export verification, checkpoint promotion, rollback recovery, and
old-journal retention before any compaction exists.

- [ ] **Step 5: Implement the durable reducer and host handoff**

Algorithm:

1. under `withOutboxTransaction`, validate the fresh closed descriptor binding,
   transition `pending_sync -> syncing`, and persist the exact fingerprint
   `PROPOSED` search action for active plus recently closed scopes;
2. the host separately dispatches and executes the read. Applying a complete
   observation with a separately refreshed successor descriptor computes its
   deterministic successor and atomically replaces the current `DISPATCHED`
   action with one `PROPOSED` action in the same outbox transaction. Without a
   fresh successor binding, the exact null fallback atomically persists
   internal `FLOW_DESCRIPTOR_STALE`/`RETRY_SAFE_READ`: an ordinary successful
   search keeps no receipt, an ACK keeps its ACKED receipt, and a unique
   ambiguous-recovery match keeps its AMBIGUOUS receipt plus
   `candidateRemoteId`. It never copies the predecessor binding. Incomplete
   search or multiple matches
   becomes a code-owned failure and never produces create;
3. one initial match atomically proposes `get_issue`; zero initial matches
   atomically proposes exactly one `create_issue` mutation whose arguments
   contain the full sanitized payload;
4. the host displays the proposed mutation and immutable batch/action digests,
   receives user confirmation, invokes `dispatch` to recheck and mark the exact
   action, then invokes it once. Applying a closed mutation acknowledgement
   with a fresh successor binding atomically persists the ACKED receipt and a
   `PROPOSED get_issue(remoteId)`; without that binding it still atomically
   preserves the ACKED receipt in safe failed recovery. An acknowledgement is
   never read-back by itself;
5. if create returns an unknown outcome, the host submits `DELIVERY_UNKNOWN`;
   the reducer records an ambiguous create receipt and recovery may plan a new
   search but never another create. A unique match atomically stores its ID as
   `candidateRemoteId` and proposes only `get_issue(candidateRemoteId)`; zero or
   multiple matches require manual reconciliation;
6. after an exact ID/title/generated-HTML/state/priority/label issue read-back,
   clear only the proven create receipt, store the remote identity, persist
   `FLOW_EVIDENCE_UNSUPPORTED`, emit no list/upload/update action, and stop in
   `failed` without `Evidence Complete`;
7. any attachment observation, attachment mutation receipt, non-null
   `evidenceCompletedAt`, or V1 transition to `synced` is invalid rather than a
   dormant future path.

Evidence unavailability and item read-back mismatch are `failed` with any
known remote identity retained. The V1 reducer can never plan
`Evidence Complete`; a later schema version must introduce and review the
entire binary-provider/read-back protocol together.

The exact guarantee is: at most one create among cooperating workers while the
single persisted create action remains current and the host invokes it once.
Strict global exactly-once requires a future server-side idempotency key bound
to the fingerprint. Ambiguous creation is never repaired by a blind second
create. The reducer itself has zero remote-call capability.

`flow-sync-cli.mjs` is the executable host boundary. Its grammar is only:

~~~text
flow-sync-cli.mjs next --fingerprint napp-v1-<64 lowercase hex> --descriptor-stdin
flow-sync-cli.mjs dispatch --action-id napp-flow-action-v1-<64 lowercase hex> --descriptor-stdin
flow-sync-cli.mjs apply --action-id napp-flow-action-v1-<64 lowercase hex> --stdin
~~~

`next` reads only the fixed production outbox plus at most 64 KiB of the closed
six-digest descriptor projection from stdin, persists or returns the one closed
`PROPOSED` action, and prints no private path, raw descriptor, or raw finding
beyond the sanitized action payload. Re-reading a proposal is safe because a
proposal cannot be executed. `dispatch` reads the same bounded fresh projection,
requires `now < expiresAt`, atomically revalidates and marks the action
`DISPATCHED`, and returns its one execution manifest; an expired proposal is
left byte-identical for a `FLOW_ACTION_STALE` observation, and any repeat after
successful dispatch returns only a summary. `apply` reads at most
96 KiB of exact
`{observation,successorDescriptorBinding}` JSON from stdin; the binding is a
fresh closed projection when the result needs a successor, or exact JSON
`null` only when the result is terminal or invokes the code-owned
`SUCCESSOR_BINDING_UNAVAILABLE` fallback described above. It
requires the exact pending action ID/digest, validates it before persistence,
and applies it under a new opaque transaction. It accepts no arbitrary file,
URL, workspace/project override, raw descriptor body, credential, Flow client,
tool name, or confirmation flag; only the exact closed descriptor projection
above is valid. The CLI snapshots and deeply freezes the bounded wrapper before
validation; the same snapshot alone reaches the transaction. The host
action-time confirmation remains in
the conversation and is required before mutation `dispatch`; it is not
fabricated or consumed by this CLI.

For a `PROPOSED` action, `next` returns the byte-identical proposal plus
`proposedAt` and `expiresAt`; stdout loss is safe because no MCP call is allowed
without `dispatch`. For a `DISPATCHED` action, `next` and repeated `dispatch`
return only
`{status:"DISPATCHED",actionId,actionDigest,kind,mutation,lifecycle,
proposedAt,dispatchedAt,expiresAt,reconciliationClass}` and never re-emit an
executable payload. `reconciliationClass` is exactly `SAFE_READ` or
`CREATE_UNKNOWN`, derived internally from the persisted kind. After dispatch
stdout loss, the host submits `FLOW_READ_FAILED` for a safe read or
`DELIVERY_UNKNOWN` for a mutation. A still-proposed expired action accepts the
truthful `FLOW_ACTION_STALE` pre-dispatch failure. The host never guesses a
mutation-specific code or blind-retries a mutation after a crash/lost result.

## Control Plane Exit Gate

This plan is complete only when:

- outbox/fingerprint/lease/sync/recovery unit tests pass;
- replay proves one contiguous digest-valid append-only journal; journaled
  lease IDs/fences close the expired-writer race; snapshot/projection drift is
  cache-only; and V1 contains no automatic compaction path;
- the production local module has no callable Flow client; the fixed-state CLI
  emits/applies only descriptor-bound action/observation records, while the
  confirmed host performs and reads back every MCP mutation;
- the workspace and project exist exactly once and are private;
- Bugs is a verified state inside NAPP;
- configuration and every coverage item have exact read-back;
- the scaffold has exactly seven states, sixteen labels including Analytics,
  and fourteen campaign coverage items including the telemetry baseline;
- unsupported view features are reported rather than fabricated;
- no invitations, objectives, automations, processes, or agents were created;
- no candidate bug was filed as confirmed;
- no telemetry-only observation was filed in Bugs;
- V1 emits no attachment/list/update action, never sets `Evidence Complete`,
  and reports `FLOW_EVIDENCE_UNSUPPORTED` after a proven item read-back;
- the telemetry coverage item read-back preserves its exact optional/add-only
  contract and records live-envelope/schema/window gaps as telemetry-only
  blockers while the deterministic campaign continues;
- cooperating workers cannot create twice while the lease is valid, and an
  ambiguous create fails closed until reconciliation instead of issuing a
  second create.
