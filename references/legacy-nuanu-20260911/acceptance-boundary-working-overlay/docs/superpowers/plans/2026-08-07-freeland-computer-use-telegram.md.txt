# Freeland Computer Use and Real Telegram Web Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a bounded local CDP daemon/CLI, deterministic real Computer Use scenarios, PostgreSQL-fenced QA personas, an OS-clipboard regression for FREEL-206, and real `web.telegram.org` Mini App attestation whose sanitized results feed the existing Freeland deterministic runner.

**Architecture:** The existing `FreelandCdpBroker` remains the sole Chrome owner and gains a private Unix-socket transport with a closed request protocol; it does not gain queues, retries, scheduling, leases, or an agent registry. A deterministic controller drives an injected host Computer Use adapter through versioned semantic actions and a pure checkpoint state machine, enforcing candidate, origin, persona-fence, cleanup, and evidence invariants before returning the existing `QaLaneExecution`. PostgreSQL 16 owns exclusive persona leases and monotonic fencing, including non-expiring `PAYMENT_HOLD`; real web, macOS clipboard, and Telegram observations are sanitized at collection time, and mocks can never satisfy a live exit.

**Tech Stack:** Node.js 20.20.x, TypeScript 6 in strict NodeNext mode, Playwright 1.61.1, Ajv 8.20, YAML 2.9, PostgreSQL 16.12, `pg` 8.16.3, macOS Chrome/CDP, macOS `/usr/bin/pbpaste` and `/usr/bin/pbcopy`, host Computer Use, and Telegram Web.

`CdpDaemonCoreDependencies` is the closed internal broker/process/ownership/
peer/authenticator dependency object in `daemon.ts`; it has no module path,
plugin name, callback name, or dynamic-loader field. N3 exports these types and
the fail-closed client. N5 alone implements the fill handler, submit handler,
submit adapter, and static payment-host composition root. N3's default registry
sets both entries to `null` and rejects both IDs as
`host_handler_not_registered`; a payment-enabled daemon must receive both
non-null entries before either socket binds. The daemon rejects a partial
registry. No N3 scenario can fill fields or submit payment.

Validate UUID fields canonically; require every nonce/digest/intent ID to be lowercase 64-hex; require positive safe payment and persona fencing epochs; require a bounded canonical window ID, persona ID, exact candidate digest, and canonical HTTPS top/frame origins without userinfo; bound opaque authorization, lease, handle, alias, and artifact IDs to 128 safe characters; require 1–16 unique registered artifact IDs; and require canonical UTC timestamps. Card values, expiry, CVV, selectors, coordinates, field names, arbitrary URLs, and secret bytes are not members of either command or result. The N5 handler resolves opaque handles inside its restricted payment boundary and must verify that every artifact ID was registered before fill.

The outer authenticated envelope supplies the exact `qaRunKey` and host
`sessionId`; the payload supplies window, candidate, persona, and both fencing
epochs. N5 must bind them into its own single-use host activation guard. The
host daemon holds one exclusive action mutex while it rereads app/window,
top/frame origin, candidate, persona epoch, permit/checkout digest, and nonce
immediately before field entry or submit. A switch after authorization but
before dispatch produces no UI action; after a durable submit claim it remains
an ambiguous consumed fence eligible only for reconciliation.
