# Freeland Payment Automation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement N5.1–N5.4 as an unattended but owner-bounded payment kernel that can perform one authorized staging canary per exact release/SKU without duplicate checkout or submit, while proving atomic budget custody, monotonic fencing, PAN/CVV deletion, independent watchdog recovery, and provider/order/entitlement reconciliation.

**Architecture:** Keep payment authorization, budget, canonical intent, checkout cardinality, submission fencing, data-custody inventory, and reconciliation in PostgreSQL 16 with database constraints and `SERIALIZABLE` transactions. Nuanu and the deterministic runner pass only immutable references; the private Mac payment adapter resolves opaque secret handles inside the declared payment boundary, and a separate watchdog scrubs CVV/PAN-bearing copies without depending on the worker callback. Routine execution consumes an owner-minted authorization without an interactive purchase Decision, but the only submit adapter remains fail-closed until every program, candidate, persona, profile, watchdog, quote, origin, budget, scrub, and reconciliation gate is present.

**Tech Stack:** Node.js 20.20.2 at `/opt/homebrew/opt/node@20/bin/node`, npm from the same installation, TypeScript 6.0.3, raw `pg` 8.16.3 with `@types/pg` 8.15.5, PostgreSQL 16.12, Node test runner through `tsx` 4.22.4, JSON Schema 2020-12 through Ajv 8.20.0, YAML 2.9.0, existing Freeland CDP/Computer Use custody, and SHA-256 canonical JSON.

## PostgreSQL Invariants and Role Boundary

Migrations create four `NOLOGIN` group roles: `freeland_payment_owner`, `freeland_payment_runtime`, `freeland_payment_reconciler`, and `freeland_payment_watchdog`. Deployment grants login principals into those groups outside Git. Tests use a migration-admin connection and `SET ROLE` to prove permissions.

All payment objects live in a dedicated `freeland_payment` schema owned by
`freeland_payment_owner`; `PUBLIC`, runtime, reconciler, and watchdog have no
`CREATE` privilege there. Every privilege-escalating routine is created as
`SECURITY DEFINER`, owned by `freeland_payment_owner`, and declares the fixed
function setting `search_path = pg_catalog, freeland_payment, pg_temp` with
`pg_temp` explicitly last. Its body schema-qualifies every table, sequence,
function, operator-sensitive expression, and extension helper and contains no
dynamic SQL. Migrations revoke all default/table/sequence/function privileges
from `PUBLIC`, then grant only exact signatures to the intended group role;
runtime is not a member of the owner role. The SQL snippets below omit the
schema prefix only for readability; implementation may not omit it.

The RBAC suite sets a hostile caller `search_path`, creates same-named tables,
functions, operators, domains, and overloads in an attacker schema and
`pg_temp`, then invokes every granted routine as runtime/reconciler/watchdog.
It proves only the owner-owned objects changed, `PUBLIC` cannot execute, no
attacker object ran, ownership cannot be reassigned, and routine output records
the original `session_user` where actor attribution is required.

`0020_payment_authorizations.sql` creates:

```sql
CREATE TABLE payment_authorizations (
  authorization_id uuid PRIMARY KEY,
  policy_revision integer NOT NULL CHECK (policy_revision > 0),
  policy_digest char(64) NOT NULL UNIQUE CHECK (policy_digest ~ '^[0-9a-f]{64}$'),
  environment text NOT NULL CHECK (environment IN ('staging', 'production')),
  full_release_sha char(40) NOT NULL CHECK (full_release_sha ~ '^[0-9a-f]{40}$'),
  product text NOT NULL CHECK (product IN ('vpn', 'esim', 'virtual-number')),
  sku text NOT NULL CHECK (length(sku) BETWEEN 1 AND 128),
  purpose text NOT NULL CHECK (purpose = 'release-canary'),
  provider text NOT NULL CHECK (length(provider) BETWEEN 1 AND 64),
  currency char(3) NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
  recurrence text NOT NULL CHECK (recurrence IN ('one-time', 'recurring')),
  max_quoted_amount_minor bigint NOT NULL CHECK (max_quoted_amount_minor > 0),
  aggregate_authorized_amount_minor bigint NOT NULL CHECK (aggregate_authorized_amount_minor > 0),
  effective_at timestamptz NOT NULL,
  expires_at timestamptz NOT NULL CHECK (expires_at > effective_at),
  resolved_profile_digest char(64) NOT NULL CHECK (resolved_profile_digest ~ '^[0-9a-f]{64}$'),
  catalog_digest char(64) NOT NULL CHECK (catalog_digest ~ '^[0-9a-f]{64}$'),
  instrument_alias text NOT NULL CHECK (length(instrument_alias) BETWEEN 1 AND 128),
  owner_subject text NOT NULL DEFAULT session_user,
  minted_at timestamptz NOT NULL DEFAULT clock_timestamp(),
  UNIQUE (authorization_id, environment, full_release_sha, sku),
  CHECK (max_quoted_amount_minor <= aggregate_authorized_amount_minor)
);
```

The same migration creates append-only `payment_program_gates`, hierarchical `payment_kill_switches`, an UPDATE/DELETE rejection trigger for authorizations and gate history, and owner-only function `owner_mint_payment_authorization(jsonb)`. Runtime receives only `SELECT` on sanitized authorization columns and `EXECUTE` on payment routines; it receives no table DML grants.

`0021_payment_ledger.sql` creates `payment_budget_ledger`, `payment_intents`, and append-only `payment_events`. `0022_payment_checkout_fencing.sql` adds `payment_instrument_mutex` and `payment_checkouts`. `0023_payment_data_custody.sql` adds `payment_submit_fences` only after the scrub tables it references exist. Required keys and checks are:

```text
payment_budget_ledger.authorization_id                 PRIMARY KEY
payment_intents.authorization_id                       UNIQUE
payment_intents.canonical_intent_id                    PRIMARY KEY
payment_checkouts.authorization_id                     PRIMARY KEY
payment_checkouts.canonical_intent_id                  UNIQUE
payment_submit_fences.authorization_id                 PRIMARY KEY
payment_submit_fences.canonical_intent_id              UNIQUE
reserved_minor >= 0 AND spent_minor >= 0 AND pending_unknown_minor >= 0
pending_unknown_minor <= reserved_minor
reserved_minor + spent_minor <= authorized_minor
checkout_count BETWEEN 0 AND 1
submitted_payment_count BETWEEN 0 AND 1
fencing_epoch > 0
```

Every state-changing routine locks only the rows it needs but preserves this
global relative order: authorization → budget → persona lease → intent →
provider ingress/finality → instrument mutex → checkout → custody → submit
fence. `packages/payment/src/postgres.ts` begins `BEGIN ISOLATION LEVEL

`0024_payment_reconciliation.sql` creates separately granted `payment_provider_handles`, append-only `payment_provider_events`, `payment_reconciliation_facts`, and `payment_reconciliation_runs`. - [ ] **Step 3: Create restricted provider-handle and fact tables**

`payment_provider_handles` stores `handle_alias`, `canonical_intent_id`, AES-256-GCM ciphertext, 96-bit IV, authentication tag, key alias, ciphertext digest, and creation time. - [ ] **Step 4: Implement the exact deterministic truth table**

- Provider `MATCHED` with `finality: FINAL`, monotonic sequence, exact amount/currency + order `MATCHED` + expected entitlement `PROVISIONED` + post-purchase `PASS`, all at the exact cutoff → `RECONCILED_PAID`, reserved decreases by settled amount, spent increases, pending unknown clears, mutex releases after persona reset eligibility.
- After a submit, provider `DECLINED` with `finality: FINAL` + order `NOT_CREATED` + entitlement `NOT_EXPECTED` + post-purchase `NOT_EXPECTED`, all at one cutoff whose `asOf >= settlementHorizonEndsAt`, remains `UNKNOWN_HELD`/`FINALITY_HOLD` until an authoritative matching `ProviderFinalityAttestation` is accepted. The acceptance transaction verifies the drained ingress watermark and then atomically emits `RECONCILED_DECLINED`, releases the reservation/mutex, and leaves submit cardinality consumed.
- A pre-submit user cancellation with zero submit may become `RECONCILED_CANCELLED` from a verified checkout-cancel fact. After a submit, provider `CANCELLED` follows the same horizon + drained watermark + authoritative terminal-closure requirement as decline; without closure it never releases automatically.
- Any `UNKNOWN`, disagreement, missing expected entitlement, wrong amount/currency, duplicate conflicting event, or post-purchase failure → `UNKNOWN_HELD`, reservation retained, `pendingUnknown = reserved`, mutex closed, payment lane paused.
- Any `PROVISIONAL` provider fact, non-monotonic sequence, mixed cutoff, future fact, decline/cancel before the horizon, missing ingress drain, or missing/untrusted terminal closure → `UNKNOWN_HELD` plus `FINALITY_HOLD`; it cannot release budget, persona, or mutex. A provider whose profile lacks authoritative closure support remains held indefinitely rather than using a timer guess.
- A higher-sequence verified `MATCHED` event observed after an accepted provider closure is a provider-contract violation. Its ingress routine uses the same canonical row locks to restore `reserved` and `pendingUnknown` to the exact charged amount, reclose/increment the instrument fence, retain consumed submit cardinality, pause `GLOBAL/*` plus environment/provider/product, append an incident event, and allow only reconciliation. It never remains a rejected event with released money.
