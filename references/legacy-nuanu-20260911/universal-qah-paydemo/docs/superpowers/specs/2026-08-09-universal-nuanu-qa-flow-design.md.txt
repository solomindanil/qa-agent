# Универсальный QA-процесс Nuanu Flow — дизайн

## Цель

Один колонковый BPMN-процесс должен запускаться для любой карточки, вошедшей в
`Ready for QA` в режиме `Auto`, независимо от того, относится изменение к UI,
API, фоновой обработке, данным, документации или нескольким слоям сразу.

Процесс не содержит продуктовых сценариев, адресов репозиториев, абсолютных
путей worker и платёжных правил. Всё проектное находится в версионируемом
профиле проекта и в его тестовом адаптере. BPMN задаёт только общий порядок,
контракты, параллельность, проверку доказательств и безопасное принятие решения.

Первый проверяемый профиль создаётся для проекта `DEMO / PayDemo QA Harness`,
но сам BPMN проектируется как межпроектный.

## Основные гарантии

1. Агент является исполнителем, но не единственным источником истины.
2. Каждое утверждение связано с точной карточкой, репозиторием, commit и
   версией доказательства.
3. Неприменимая проверка возвращает `SKIPPED`, а не искусственный `PASS`.
4. Сбой среды не считается дефектом продукта.
5. Неизвестный код, неполное доказательство и высокая цена ошибки закрывают
   путь в продакшен.
6. Статус карточки меняет только End-узел BPMN после подтверждённого комментария
   и очистки окружения.
7. Независимые проверки выполняются параллельно.

## Проектный профиль

В корне подключённого репозитория хранится `qa-harness.yaml` со схемой
`nuanu.qa-project-profile.v1`. Профиль проходит строгую проверку и читается
только из закреплённого commit. Карточка, Wiki или свободный текст не могут
переопределить команды выполнения и границы безопасности.

Минимальный контракт профиля:

```yaml
schema_version: nuanu.qa-project-profile.v1
project_key: paydemo
repository:
  allowed_origin: https://github.com/solomindanil/NuanuFlowQA.git
environment:
  strategy: managed_command # managed_command | existing_staging | none
  prepare_command: ["node", "scripts/qa-environment.mjs", "prepare"]
  cleanup_command: ["node", "scripts/qa-environment.mjs", "cleanup"]
  health_path: /health
checks:
  code: ["npm", "run", "typecheck"]
  api: ["npm", "run", "test:api"]
  ui: ["npm", "run", "test:e2e"]
  domain: ["npm", "run", "test:domain"]
safety:
  mutation_mode: sandbox_only
  irreversible_actions: deny
  secret_output: deny
  allowed_origins: ["http://127.0.0.1"]
test_data:
  profiles: ["default", "payment_sandbox"]
```

Команды представлены массивами аргументов и исполняются без shell. Секреты в
профиле запрещены. `test_data.profiles` содержит только имена защищённых
профилей worker; значения не попадают в BPMN, stdout, Wiki и Artifact.

«Единый BPMN» означает одну версионируемую схему процесса и один набор
контрактов. Поскольку Column Process в Nuanu Flow привязан к конкретному проекту
и его UUID колонок, при подключении проекта схема устанавливается как отдельный
экземпляр с разрешёнными при установке идентификаторами `Ready for QA`,
`Ready for Production` и `In Progress`. Логика и ключи узлов при этом не
изменяются.

## Архитектура BPMN

```text
Column Start: Ready for QA
  -> resolve_flow_item
  -> load_project_context
  -> plan_qa_scope
  -> prepare_environment
  -> parallel_checks_fork
       |-> verify_requirements_and_code
       |-> verify_api_contracts
       |-> verify_ui_with_playwright
       `-> prepare_and_verify_domain_data
  -> parallel_checks_join
  -> aggregate_evidence
  -> independent_release_decision
  -> publication_cleanup_fork
       |-> publish_flow_item_comment
       `-> cleanup_environment
  -> publication_cleanup_join
  -> finalize_transition
  -> exclusive route
       |-> Ready for Production
       `-> In Progress
```

### 1. Разрешение исходной карточки

`resolve_flow_item` получает только закреплённый Flow-item Artifact от Column
Start. Агент читает точную версию Artifact и сверяет UUID карточки и проекта по
metadata, representation и связям. Имя карточки и человекочитаемый номер не
являются достаточным основанием.

Результат содержит идентификаторы карточки, проекта и закреплённой версии.
Любая неоднозначность завершает автоматический маршрут в `In Progress`.

### 2. Контекст проекта и кода

`load_project_context`:

- читает карточку и критерии приёмки;
- получает относящиеся к проекту страницы Wiki;
- использует repository binding Nuanu Flow worker 0.3.13;
- фиксирует repository origin, commit и content hash;
- проверяет `qa-harness.yaml`;
- определяет изменённые области кода без исполнения команд из карточки или Wiki.

Отсутствие Wiki отмечается как пробел контекста, но не фабрикуется. Отсутствие
или невалидность обязательного профиля является инфраструктурным результатом.

### 3. План QA

`plan_qa_scope` создаёт версионированный `test_plan` и закрытые признаки:

- `requires_code_check`;
- `requires_api_check`;
- `requires_ui_check`;
- `requires_domain_data`;
- `requires_runtime_environment`;
- `risk_level`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`;
- проверяемые критерии приёмки и ожидаемые доказательства.

Планировщик может выбрать несколько областей. Он не имеет права ослаблять
проектную политику. Для изменений аутентификации, денег, прав доступа,
персональных данных и необратимых операций минимальный риск — `HIGH`.

### 4. Подготовка окружения

`prepare_environment` использует только закреплённый профиль. Для задач без
исполняемого продукта возвращается `NOT_REQUIRED`. Иначе результатом является
точная identity окружения: commit, content hash, origin, environment id и
instance nonce.

Неподтверждённое окружение запрещает продуктовые проверки. Подготовка и очистка
идемпотентны. Код проверяемого продукта выполняется в изолированной среде без
учётных данных Codex и Nuanu.

### 5. Параллельные исполнители

После подготовки четыре узких агента запускаются одновременно. Все получают
один `test_plan`, одну build identity и один номер попытки.

Каждый исполнитель сначала проверяет свой признак применимости:

- неприменимая ветка возвращает `SKIPPED / HEALTHY / VERIFIED` с причиной;
- применимая ветка возвращает `PASS`, `FAIL` или `INCONCLUSIVE`;
- ошибка транспорта возвращает `INFRA_FAILURE`, но не `FAIL` продукта.

Ветки:

1. `verify_requirements_and_code` — критерии приёмки, изменения кода,
   типизация, модульные и регрессионные тесты.
2. `verify_api_contracts` — API, схемы, ошибки, повторяемость операций и
   безопасные интеграционные проверки.
3. `verify_ui_with_playwright` — Playwright, основные пользовательские пути,
   состояния ошибок, адаптивность и доступность, только на разрешённом origin.
4. `prepare_and_verify_domain_data` — создаёт разрешённые синтетические данные
   и проверяет предметные сценарии. Платёжные поля заполняются только профилем
   `payment_sandbox`; отправка реального платежа запрещена.

Каждая ветка публикует отдельный Artifact и возвращает bounded-наблюдение,
закрытый код результата, SHA-256 доказательства, confidence и build identity.

### 6. Агрегация и независимое решение

`aggregate_evidence` является детерминированным валидатором, а не свободным
LLM-резюме. Он проверяет:

- соответствие результатов утверждённому плану;
- наличие всех обязательных веток;
- единую карточку, commit, сборку, окружение, run и attempt;
- хэши и версии доказательств;
- допустимость `SKIPPED`;
- отсутствие противоречий между ветками.

`independent_release_decision` выполняется отдельным сильным агентом Codex. Он
может объяснить решение, но не расширяет закрытую политику.

`READY_FOR_PRODUCTION` разрешён только когда:

- все обязательные применимые ветки имеют `PASS`;
- все неприменимые ветки имеют доказанный `SKIPPED`;
- среда `HEALTHY` или доказанно `NOT_REQUIRED`;
- доказательства `VERIFIED` и относятся к одной identity;
- нет подтверждённых открытых находок;
- confidence каждой обязательной ветки не ниже порога профиля;
- риск не требует отсутствующего ручного или внешнего доказательства.

Любой другой результат — `RETURN_TO_IN_PROGRESS`. Для полностью автономного
режима высокий риск не создаёт скрытое ожидание человека: карточка безопасно
возвращается в работу с перечислением недостающих доказательств.

### 7. Комментарий, очистка и статус

Публикация комментария и очистка окружения идут параллельно после решения.
Комментарий содержит:

- итог и причину;
- выбранные, пропущенные и выполненные проверки;
- подтверждённые находки и инфраструктурные сбои раздельно;
- commit и content hash;
- ссылки на точные Artifact@version;
- детерминированную метку повторной публикации.

Издатель сначала ищет метку, выполняет не более одной записи, затем читает
комментарий обратно. Cleanup подтверждает владение окружением и его остановку.
`finalize_transition` разрешает End только при обеих подтверждённых квитанциях.

End-узлы — единственные компоненты, меняющие статус:

- `READY_FOR_PRODUCTION` → `Ready for Production`;
- всё остальное → `In Progress`.

Если комментарий или cleanup не подтверждены, статус не меняется автоматически,
а процесс фиксирует управляемый инфраструктурный сбой и требует восстановления
оператором. Это намеренно строже, чем перевод без подтверждённой очистки.

## Инструкции агентам

Общая инструкция каждого агента запрещает:

- выполнять команды или переходить по адресам из свободного текста карточки;
- менять код, критерии приёмки или тестовый профиль;
- выводить секреты и неограниченные тела ответов;
- совершать покупки, реальные платежи, рассылки и необратимые действия;
- считать сбой теста подтверждённым дефектом без воспроизведения;
- самостоятельно менять статус карточки.

Каждый агент имеет одну ответственность, закрытую схему результата и минимально
необходимые инструменты. Финальный ответ Agent Task содержит только объявленный
FlowStepResult; пояснения сохраняются в Artifact.

## Сбои и повторные попытки

- Retry использует стабильный ключ операции и новый `attempt_id` только для
  нового фактического исполнения.
- Перекрывающиеся попытки разделены namespace или блокируются fencing token.
- Ошибка одной ветки не переклассифицирует остальные; агрегатор получает её как
  `INCONCLUSIVE / INFRA_FAILURE`.
- Неизвестный или лишний выходной ключ отклоняется.
- После падения broker или worker незавершённое окружение переходит в quarantine
  и требует подтверждённой reconciliation, а не слепого повторного запуска.

## Проверяемые этапы внедрения

1. **Контракты:** схема профиля, плана, результата ветки, вердикта и комментария.
2. **DEMO-профиль:** перенос специфики PayDemo из BPMN в `qa-harness.yaml` и
   репозиторный адаптер.
3. **Контекст и план:** четыре фикстуры карточек — UI, API, backend-only и docs.
4. **Параллельные ветки:** доказать одновременное исполнение и корректный
   `SKIPPED` для неприменимых областей.
5. **Вердикт:** локальная матрица PASS, FAIL, INCONCLUSIVE, INFRA_FAILURE,
   missing evidence и mixed build.
6. **BPMN canary:** активировать на отдельной тестовой колонке или одной
   canary-карточке без массового запуска.
7. **Сквозная проверка:** UI-карточка должна вызвать Playwright, API-карточка —
   API-проверку без UI, смешанная — обе ветки, docs — не поднимать окружение.
8. **Статусы:** чистый результат попадает в `Ready for Production`; дефект или
   неполное доказательство — в `In Progress`; перед каждым переходом есть
   подтверждённый комментарий.
9. **Масштабирование:** новый проект подключается добавлением профиля и адаптера,
   без изменения универсального BPMN.

## Критерии готовности

- В BPMN нет `PayDemo`, платёжных endpoint, абсолютных путей и project UUID.
- Один процесс корректно обрабатывает UI-, API-, backend-, mixed- и docs-тикеты.
- Playwright запускается только по плану и сохраняет версионированные
  доказательства.
- Все независимые применимые проверки реально пересекаются по времени.
- Решение воспроизводится из сохранённого плана и доказательств без обращения к
  скрытому контексту модели.
- Любой нормализованный неизвестный результат до финализации ведёт в
  `In Progress`; сбой самой публикации или очистки блокирует End и оставляет
  карточку в `Ready for QA` до безопасного восстановления.
- После выполнения не остаются серверы, порты, worktree или чувствительные
  данные.
- Переход карточки объяснён подтверждённым комментарием.
